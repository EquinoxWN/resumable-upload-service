# M1 test results

Recorded 2026-11-14 on the author's machine (Intel Core i7-13700H, 20 logical cores, 13.7 GB RAM,
Windows 11, Node.js 24.19.0, npm 11.17.0, TypeScript 7.0.2). Other builds ran in parallel on the same
machine, so timings are indicative. CI re-runs lint, tests and the audit on Node.js 24 on every push.

## Tests: 59 passed, 0 failed

Command: `make test` (`npm test`: compile with `tsc`, then `node --test --test-concurrency=1` over
`dist/test/*.test.js`). About 5 s. Every server test starts a fake S3 (`src/testing/fakes3.ts`) and the
tus server on random local ports; fake S3 data and upload state live in `.tmp/t-*` and are removed by
each test. The fake recomputes the SigV4 signature of every request, checks `x-amz-content-sha256`
against the body, and enforces S3's multipart rules (part order, ETags, minimum part size, set to
64 KiB in tests so uploads stay small).

## End to end against moto (`npm run e2e:s3`)

moto 5.2.5 (`moto[server]`, installed into `.tmp/moto-venv` and removed afterwards) on 127.0.0.1:5055,
with the server's real minimum of 5 MiB per part. Result line:

```
E2E PASS: 11534339 bytes in 3 parts, kept 7340032 bytes after the cut, 0 client resumes, sha256 6c7f766c8673ba81; termination aborted the multipart upload
```

The run sends 7 MiB of an 11 MiB + 3 byte upload on a raw socket and cuts it; `HEAD` reports all
7 MiB kept (one 5 MiB part in S3, 2 MiB spooled); the client sends the rest in 3 MiB chunks; the
object read back from moto has the same SHA-256. A second upload with one stored part is deleted and
no object is left. The first run of this check showed a defect, recorded below.

## Memory benchmark (`make bench`)

`node dist/src/bench.js <MiB> [partMiB]`: the tus server runs in a child process started with
`--expose-gc`; every 50 ms it forces a GC and records RSS and live memory (heap used + external +
array buffers). The parent runs the fake S3 (writing to `.tmp/bench-*`, removed afterwards) and the
client, which sends generated data in 8 MiB `PATCH` requests. Every run checked the stored object's
SHA-256 (`intact: true`).

| Upload | Part size | Parts | Time | Server RSS base / peak | Server live base / peak |
|---|---|---|---|---|---|
| 32 MiB | 5 MiB | 7 | 0.60 s | 69.9 / 81.5 MiB | 11.4 / 31.9 MiB |
| 128 MiB | 5 MiB | 26 | 3.72 s | 69.8 / 87.6 MiB | 11.6 / 42.2 MiB |
| 256 MiB | 5 MiB | 52 | 9.07 s | 69.2 / 86.8 MiB | 11.4 / 40.8 MiB |
| 256 MiB | 16 MiB | 16 | 6.40 s | 69.3 / 112.4 MiB | 11.4 / 99.3 MiB |

Peak memory does not grow from 32 to 256 MiB; it grows with the part size. With 5 MiB parts the live
peak is about 30 MiB above the base: the part buffer, the client's 8 MiB request body arriving in
socket buffers, and the part being signed and sent. Throughput is not a goal of M1 (the fake S3 writes
every part to disk and then joins them, in the same process as the client).

## Quality control (DMAIC)

| Phase | This repository |
|---|---|
| Define | Large uploads over unreliable connections restart from zero and buffered servers run out of memory. M1 counts when a tus client can resume after any drop with no received byte lost, every stored object matches the upload, parts follow S3's rules, and memory does not grow with file size ([RFC 0001](../rfc/0001-design.md)). |
| Measure | 59 tests, strict `tsc`, `npm audit`, the moto end-to-end run and the memory benchmark above, on an Intel Core i7-13700H with Node.js 24.19.0. |
| Analyze | All objects matched their SHA-256. Server peak RSS stayed at 81-88 MiB from 32 to 256 MiB with 5 MiB parts and rose to 112 MiB with 16 MiB parts, so memory follows the part size. Defects found while building (below) were all in failure paths: what the server reports after an interrupted request, and what a client sees while a request is still saving. |
| Improve | (1) After an interrupted `PATCH` the reported offset was the one from before the request although the bytes were saved; it is now recomputed from the saved state. (2) The moto run showed `HEAD` answering during a `PATCH` that was still saving its tail, so the client saw 5 MiB instead of 7 MiB and needed a 409 round trip; `HEAD` now waits up to 3 s for the lock (moto run then: 0 client resumes). (3) The client looped forever when its source returned fewer bytes than asked; it now fails that attempt. (4) A second `close()` of a server threw and left test scratch behind; `close()` is now idempotent. (5) Two hand mutations survived (a part flushed one byte early, bytes past the length not cut by one byte); two tests now kill them. |
| Control | CI `build` job: `make ci` (strict `tsc`, 59 tests) and `make audit` on every push and pull request; CI `s3-e2e` job: the moto run with a `::notice` result line. The fake S3 rejects short parts, bad ETags, wrong order and bad signatures, so a regression in part sizing or signing fails tests. Configuration is validated at start (exit 2). |
