# Quality check against the 10 rules (2026-11-01 checklist, run 2026-11-14)

Run on Windows 11 (Intel Core i7-13700H) with Node.js 24.19.0 while M1 was built. Mutations were
applied one at a time by a script that runs `npm test` and restores the file afterwards.

| # | Rule | Status | Evidence |
|---|---|---|---|
| 1 | Assume every call can fail | pass | Every S3 call has a per-attempt deadline (`AbortSignal.timeout`, `S3_TIMEOUT_MS`), up to 3 attempts with jittered exponential backoff for 429/5xx/transport errors, none for 4xx (`s3.ts` `call`); responses are capped at 1 MiB. Client requests have deadlines and bounded retries (`client.ts`). Incoming `PATCH` bodies have an idle timeout; stalled and dropped bodies keep their bytes. Errors are logged and answered (500/502/503), not swallowed; the client's `HEAD` failure after a failed `PATCH` is retried and counted through the next `PATCH`. Tests: timeouts, cut connections, injected 5xx and 4xx. |
| 2 | Writes safe to retry | pass | State files: temporary file, fsync, rename (`store.ts` `atomicWrite`). `UploadPart` with the same part number overwrites; a part is recorded only after S3 answered. A retried `CompleteMultipartUpload` answered `NoSuchUpload` is checked with `HeadObject`. `PATCH` at a stale offset is 409 (no double append). Tests: re-sent part, lost Complete answer, 409, restart. |
| 3 | No race conditions | pass | One `PATCH` per upload (lock taken with no `await` between check and set; 423 otherwise); `DELETE` takes the same lock; `HEAD` waits for it. Tests: concurrent `PATCH` gets 423 and the upload is intact; `HEAD` during a running `PATCH`. |
| 4 | Don't trust the clock | pass | Durations in tests and the benchmark use `performance.now`; deadlines use timers. Stored `createdAt` and log lines are ISO 8601 UTC. `x-amz-date` is wall-clock UTC by protocol. Nothing is ordered by timestamps (parts by number). |
| 5 | Read before changing | pass | Node APIs used exist in Node 24 (`req.iterator({ destroyOnReturn })`, `server.closeAllConnections`). Every environment variable read in `config.ts` is in the README table; every path in the docs exists (`audit_repo.py`). |
| 6 | Never break compatibility | pass | tus 1.0.0 headers and status codes as in the specification; info files are validated on load, and a corrupt file is an error instead of a reset. First release, no earlier format to keep. |
| 7 | One source of truth | pass | The info file is the source of the offset (parts + recorded spool size); bytes in the spool beyond the recorded size are ignored (ADR 0003). Node 24 in `engines`, CI and docs; moto 5.2.5 in CI and results. |
| 8 | Small changes, no secrets, validate input | pass | Secret grep: test keys are obvious placeholders (`TESTACCESSKEY`, `test-only-secret-not-a-real-key`, the AWS documentation's example key). Every header is parsed with limits (digits only, safe integers, metadata 4 KiB, MIME type pattern for content type), upload ids must be UUIDs before any path is built, configuration is validated (exit 2). No runtime dependencies. |
| 9 | Tests that can actually fail | fixed | No tautologies or skips. 10/12 mutants killed before, 12/12 after (two tests added, table below). |
| 10 | Re-verify | pass | Lint, tests, audit and `audit_repo.py` below; the moto end-to-end run passed; CI not yet run. |
